# 真机内存布局：更正与共用结论

## 一、更正（我此前两处判断有误）

### 1. 真机 MemTotal 确实是 129 MB，不是 1.25 GB

我此前只看到 cmdline 的 `mem=1G@0` + `mem=256M@0x80000000@1`，误当成总内存。
实际 `memrsv` 把绝大部分保留掉了：

```
声明 mem            = 1280 MB
保留合计            ≈ 1139.5 MB
  1M@0 + 32K@0xF00000 + 27.6M@0x02E68000 + 174.9M@0x0A915000
  + 680M@0x15800000 + 256M(bank1)
推算可用            ≈ 140.5 MB
实测 MemTotal       = 128,796 kB = 125.8 MB   ← 差值即内核自身开销
```

对照真机 /proc/meminfo：
```
MemTotal:  128,796 kB
MemFree:     2,904 kB      <- 空闲只剩 2.8 MB
```

结论：**129 MB 是 MemTotal，是真机真实可用内存**。我错了。

### 2. 崩点是用户态 VA 未映射，不是"物理内存不存在"

QEMU 机器模型 DDR0 = 1GB@0、DDR1 = 256MB@0x80000000，物理上都存在。
所以 0x096000E4(150MiB) / 0x0A6000E4(166MiB) **在物理层面是 RAM**。
崩的是**进程页表里没有这页**（用户 VA 未映射）。

我此前"超出物理范围所以 abort"的假设不成立。

## 二、真机 bank0 可用/保留分布（移植侧算出，已核对）

```
0x00000000-0x00100000   1.0 MB    保留
0x00100000-0x00F00000  14.0 MB    可用
0x00F00000-0x00F08000  32 KB      保留
0x00F08000-0x02E68000  31.4 MB    可用
0x02E68000-0x048C6000  26.4 MB    保留
0x048C6000-0x0A915000  96.3 MB    可用   <- 崩点落在这里
0x0A915000-0x15800000 174.9 MB    保留（GPU/CP 类）
0x15800000-0x40000000 680 MB      保留（:uc）
```

核对：0x096000E4 = 150.0 MiB、0x0A6000E4 = 166.0 MiB，
**两者都落在 0x048C6000..0x0A915000（普通可用 RAM）内**。
真机最靠上的可用地址 = 0x0A915000 = 169 MiB。

## 三、共用结论

1. **"窗口放在 0x08000000"是 QEMU 侧的选择，不是真机布局。**
   真机那一带就是普通 RAM，真正的 carve-out 是 0x0A915000 起的 175MB。
2. **崩点 = 窗口末 + 0x6000E4（两次完全一致）**
   => 单纯加大窗口不收敛（64MB 时会崩在 0x0C6000E4）。
3. **正确方向是"映射大、报告小"**：
   - QEMU 的 VM 有 DDR0=1GB，**映射大方一点是免费的**（真机只有 129MB，才需要抠）
   - 映射覆盖到至少 `报告大小 + 6MiB`，稳妥做法是一次映射 128~256MB，
     但 mmap 返回给 App 的 size 仍按请求值报
   - 映射必须用连续保留物理区 + `remap_pfn_range` 一次调用，不要 vmalloc 逐页
4. **窗口基址/大小不是固件常量**：移植侧已查过 appFw/libObj，
   0x08000000 的命中多为重定位/指令噪声，0x0A915000 在 appFw .data 仅一处且未对齐，
   不可作边界依据。=> 它是驱动 mmap 与 App 协商出来的。
