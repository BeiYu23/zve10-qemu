## 二、五个面的三项指标

| 面 | RGB565@640×480 | DOWN 前后 | 结论 |
|---|---|---|---|
| **stream@20312000 (32MB)** | 113 色 / 行差 31.5 / 非零 100% | **变化 7 次** | **活跃命令环** |
| stream@22312000 (4MB) | 4 色 / 行差 1.24 / 非零 100% | 0 次 | 静态空表 |
| **stream@3f7ed000 (8MB)** | 859 色 / 行差 87.4 / 非零 81.2% | 0 次 | **wbi_cmpr 压缩数据** |
| mem@3f3ec000 (4MB) | 17 色 / 行差 3.09 / 非零 **0.4%** | 0 次 | 近乎空 |
| mem@80000000 (8MB, wo) | 3461 色 / 行差 94.3 / 非零 100% | 0 次 | 噪声 |

### 实际 dump 看图（决定性）

**`stream@3f7ed000` 按 RGB565 渲染 ⇒ 重复竖带 + 密集横纹**（换 4096/2048/1280 宽度都一样）
**⇒ 压缩数据，与 zv-e10-re 记录的 `wbi_cmpr` 一致。**

**`mem@80000000` ⇒ 纯彩色噪声 ⇒ 未初始化或非 RGB565 排布。**

## 三、sysfs 模块引用计数（打开菜单前后）

```
before:  grm_ma=0  dmm=2  grm_gles=2  liro=0
after:   grm_ma=0  dmm=2  grm_gles=2  liro=0
```

**★★★ `grm_ma` 始终为 0 ⇒ 真机上 UIPC 同步发送路径**没有**在用 MA 的 mspace。**

**⇒ QEMU 里 `grm_ma` mspace 垃圾导致 oops，可能是**模型自身初始化问题**，
不是真机的必需路径。**

## 四、★★★ 推论：绘制的正确姿势是**提交命令**，不是写像素

```
App 写命令到 /dev/stream @0x20312000 环
        ↓
RTOS 解释、硬件执行
        ↓
面板
```

**⇒ 如果我们要"画东西"，需要：**
1. **搞清描述符/命令的编码格式**
2. **向环里追加我们自己的绘制命令**
3. **让 RTOS 处理它**

**★★★ 这正好解释了 A7M3 怎么玩贪吃蛇（同代 CXD90045）：**
**它多半是**提交绘制命令**，而不是直接写帧缓存。**

**⇒ 下一步的关键实验：**
**按 DOWN 前后对 0x20312000 做**精确字节差分**，找出哪些偏移变了、
变化模式是什么（序列号递增？命令码？坐标？），从而反推命令格式。**
