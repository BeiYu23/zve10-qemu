# 对"GPU 窗口必须 >32MB"这一判断的复核

## 一、结论速览

| 对方的判断 | 复核结果 |
|---|---|
| 崩点 = base + 窗口大小 + ~6MB | 数据成立 |
| 因此 App 需要更大的窗口 | 不完整：加大只会把崩点推着走，不收敛 |
| 下一步试 64MB，再试 128MB | 大概率白跑：预测崩在 0x0C6000E4 |
| 真机内存只有 129MB | 事实错误：真机 1G + 256M |
| 大窗口必须靠 memmap 预留 | 手段可行，但不是真机做法；边界应从真机 cmdline 取 |
| SIGILL 与"窗口内容非法"相关 | 更可能是坏函数指针 |

## 二、窗口加大不收敛（算术实证）

```
16 MB 窗口 → 窗口末 0x09000000 → 崩溃 0x096000E4 → 越过窗口末 0x6000E4
32 MB 窗口 → 窗口末 0x0A000000 → 崩溃 0x0A6000E4 → 越过窗口末 0x6000E4
```

两次"越过窗口末"的偏移完全相同。说明访问点不是固定绝对地址，而是
`窗口末 + 0x6000E4`。窗口提到 64MB 时，崩点应精确落在 `0x0C6000E4`。

**建议改为把"实际映射大小"与"报告给 App 的 size"解耦**：
映射一大片（如 128MB），但 mmap 返回的 size 仍按 App 请求的值报告。
- 崩点消失 ⇒ 是连续性/竞技场问题（App 以为 VA 后面还有内存）
- 仍崩在 +6MB ⇒ 是 size 协商本身有问题

## 三、真机的内存与保留区（KEMCO.TXT 实证）

真机 `/setting/KEMCO.TXT`（1925 字节，从相机读出的原件）：

```
mem=1G@0
mem=256M@0x80000000@1
memrsv=1M@0
memrsv=0x8000@0xF00000
memrsv=0x1A5E000@0x02E68000
memrsv=0xAEEB000@0x0A915000      <- 约 175MB，起始 0x0A915000
memrsv=680M@0x15800000:uc
```

要点：

1. 真机是 1G + 256M = 1.25GB，不是 129MB。若 129MB 来自 /proc/meminfo 的
   MemFree，那是空闲量而非总量。若 QEMU VM 本身只给约 129MB RAM，则
   0x096000E4(150MB) 与 0x0A6000E4(166MB) 都在物理范围之外，
   任何访问都会 data abort，与窗口大小无关。**这条应优先排除。**
2. 真机 cmdline 里 `memmap=` 出现 0 次，用的是 `memrsv=`。
   所以 memmap 是 QEMU 侧的替代手段，可行，但不是真机做法。
3. 真机的保留区从 `0x0A915000` 开始，就在 32MB 窗口末 `0x0A000000` 之上约
   9MB 处。崩溃地址 `0x0A6000E4` 正落在两者之间——真机那里是普通 RAM，
   QEMU 里被 memmap 挖掉了。

**因此窗口边界建议取 `0x08000000 .. 0x0A915000`，约 41MB**，
这是从真机 cmdline 推出来的真实边界，比猜 64/128 更可靠。

## 四、SIGILL 的另一种解释

在 libc 区（0x04483b6x~7e）执行到 SIGILL，典型原因是 Thumb 位错误的函数指针
（BLX 跳到 ARM 字地址，CPU 解出非法指令），或代码页被覆盖，而不是"窗口内容非法"。

建议单独记录 SIGILL 的 pc / lr / code：若 lr 来自 App 的回调，就是坏函数指针；
若 pc 落在被映射窗口内，才是内容问题。

## 五、建议顺序

1. 先确认 QEMU VM 的 RAM 是否 >= 1GB，与真机对齐（这条最可能是一切的根因）
2. 窗口设为 `0x08000000 .. 0x0A915000`（约 41MB），或采用"映射大、报告小"
3. 单独抓 SIGILL 的 pc / lr / code，与窗口问题分开排查
4. 暂停 64 -> 128MB 的盲目加倍
