# 新引擎 + ZV-E10 老菜单内容：适配评估（纯离线）

> 目标变更：**保留 ZV-E10 的菜单内容**（`share/app` 资源），换成 ZV-1F 的新引擎
> （`appFw.so` + `libObj.so`）。本文评估"能否适配"。

---

## 一、✅ 格式层：**确认兼容，不需要适配**

### 1.1 容器头逐字节相同

```
global.xdb    E10 12252 B / F 13320 B
  头部 20 字节: 75786107 00000000 09000000 efe01d00 00000000   ← 完全相同
                  magic "uxa\x07"  ver=0    +8=9               +16=0

.uxc          magic "uxc\x07"  ver=0                        ← 完全相同
```

**⇒ magic、版本号、`+8` 字段（=9）全部一致 ⇒ 同一版解析器。**

### 1.2 最直接的证据：`LayoutMaster_Menu.uxc` 98% 字节相同

```
ZV-E10  3,512 B
ZV-1F   3,636 B
共同前缀: 3,440 字节 = E10 全文件的 98.0%
```

**⇒ 两版连"布局主表"的内容几乎一样。**

### 1.3 ★ ZV-E10 本来就用同一套 DSL

```
ZV-E10 share/app 也有: LayoutMaster_Menu.uxc
                       master_browser / master_camera / master_network / master_other
ZV-1F  share/app 另有: LayoutMaster_Other.uxc, master_normal.uxc
```

**⇒ 两版不是"不同架构"，是【同一布局系统 + 不同内容】。**

### 1.4 同名文件 77 个（含全部框架资源）

`color_cmn` / `style_cmn` / `lang_cmn` / `LayoutMaster_*` / `master_*` / `string_*` × 35

## 二、`.uxc` 是**索引式**记录（小整数 ID，不是自由格式）

最小的 `viewBaseMenu.uxc`（84 B）全文：

```
0x00  magic "uxc\x07"   0x04 ver=0
0x08  08 00 8d 00        ← 两个 u16 字段（0x0008 / 0x008D）
0x0C  01 20 00 00
0x20  02 00 00 00        ← 2
0x28  09 00 00 00        ← 9
0x30  38 00 00 00  39 00 00 00  3a 00 00 00  3a 00 00 00
      ↑ 一串小整数（0x38/0x39/0x3A/0x3A）⇒ 索引/ID，不是任意数据
0x40  全 0
```

**⇒ 布局文件由"小整数 ID 序列"构成，引擎按 ID 表解释。**

## 三、⚠️ ID 词表重叠：97.4%，但**这个数字不可信**

```
ZV-E10（40 个 view*.uxc）: 352 种 ID
ZV-1F （16 个非字符串文件）: 2,935 种 ID
共有 343 种 ⇒ "ZV-E10 被覆盖 97.4%"
```

**⚠️ 这个指标有严重偏差**：ZV-1F 侧样本里小整数出现 52,571 次（vs ZV-E10 的 3,852 次），
**随机小整数必然大量重合**。

**⇒ 它是"共同前缀"那类代理指标的同类问题：数字看起来很好，但不回答真正的问题。**
**⇒ 不能据此说"词表兼容"。**

## 四、⇒ 适配评估的诚实结论

| 层 | 状态 |
|---|---|
| **容器格式** | ✅ **确认兼容**（magic / ver / +8 / 头 20 B 全同） |
| **布局 DSL 家族** | ✅ **同源**（ZV-E10 本来就有 LayoutMaster/master_*） |
| **布局主表内容** | ✅ **98% 相同** |
| **ID / 动作词表语义** | ❌ **离线无法判定** |
| **引擎是否接受老内容的动作** | ❌ **离线无法判定** |

**⇒ 格式层没有任何需要"适配"的地方；语义层无法离线判定。**

## 五、如果实测失败，可能的适配点（按可能性）

| # | 可能问题 | 适配方法 |
|---|---|---|
| 1 | 新引擎按 `+8`(=9) 或内部字段读特定段，老文件段布局不同 | 用新版 `global.xdb` 的骨架 + 老版的屏幕条目**重新生成** |
| 2 | 老 `.uxc` 引用了新引擎没有的动作 ID | 反查新引擎的动作分发表，补实现或改布局 |
| 3 | 老内容的资源 ID 与新框架文件冲突 | 重编 ID / 加偏移 |
| 4 | 屏幕清单来源不同（新引擎不读老 `global.xdb` 的屏表） | patch 引擎的屏表读取点 |

**⇒ 4 条都需要知道 `.uxc` 的完整语法，才能动手。**

## 六、建议的下一个分析（纯离线，最有价值）

**反推 `.uxc` 的语法（opcode/字段边界）**，方法是：

从"只差几个字段"的文件对中反推出字段边界与含义。

**⇒ 有了语法，上面 4 条适配点全部可操作；没有语法，只能靠试。**
