# `0x085360E4`：App 期望的是**恒等映射的 GPU 窗口**，不是"随便给个 VA"

## 一、从你的日志能直接推出来的结论

```
FAKEGLES mmap  va=0x09C6C000 size=0x20000     ← App 只映射了 128 KB，得到 VA 0x09C6C000
崩溃：address=0x085360E4                      ← 但它往 131 MB 处写
pc: str.w r3,[r0],#4  with r0=r4=0x085360E4   ← 批量拷贝的目标地址
```

**它写的地址（0x085360E4）和它 mmap 得到的地址（0x09C6C000）毫无关系。**

⇒ **这个地址不是从那次 mmap 得到的**，App 是在"按自己认为的窗口基址"直接访问。

## 二、查了：没有 0x08000000 硬编码基址

| 库 | `0x08000000` 常量 |
|---|---:|
| **`appFw.so`** | **0 处** |
| `libObj.so` `.data` | 344 处，但**上下文是参数默认值表**，不是窗口表 |

`libObj.so` `.data` 里命中处的上下文：
```
00000000 0112f000 08031238 0111f000 00000000 0202f000 10000004 0116f000
08000000 0117f000 00000001 0044f000 00000000 0010f000 12345678 ...
```
`0112f000 / 0113f000 / 0116f000 / 0117f000 / 0044f000` 是 **0xPPPP0000 形式的参数 ID**，
`0x08000000` 只是其中某个参数的**默认值**。

⇒ **不是"硬编码 0x08000000 基址"**。

## 三、★ 真正的机制：真驱动做的是**恒等映射**

Sony 这套 GPU 窗口的惯例是：**物理地址 == 用户态虚拟地址**
（`grm_gles.ko` 用 `remap_pfn_range` 把物理窗口按**同一地址**映射进进程）。
这样 App 就能直接拿物理/窗口地址当指针用 —— 这正是它现在干的事：
**直接往 `0x085360E4` 写，期待那里已经是自己的可写页。**

而 `fake_gles` 把它映射到了**另一个 VA（0x09C6C000）** ⇒ App 实际要写的那个地址
在自己页表里**没有映射** ⇒ `trap 0x0e`。

⇒ **这与"库是谁"无关、与"ioctl 号"无关，是地址映射语义不等价。**

## 四、对你两个方案的判断（重要）

| 方案 | 评价 |
|---|---|
| **A：vmalloc 大缓冲 + 逐页 `remap_pfn_range`** | ❌ **单独做不够**：映射出来的 VA 仍由内核选（比如又给你一个 0x09C6xxxx），App 还是去写 0x085360E4 ⇒ **照样崩** |
| **B：预留一段 DDR 物理区 + 整段映射** | ✅ **方向对**，但**必须恒等映射**：物理 `X` 映射到虚拟 `X` |

### 推荐做法（A+B 合体，但要恒等）

```
1) init 时预留一段物理 DDR（例如 phys 0x08000000 起，64 MB → 覆盖到 0x0C000000）
   或用 memblock_reserve / request_mem_region 保住它不被别人用
2) fake_mmap 里：把该物理段的 pfn 用 remap_pfn_range 映射进 vma，
   并且让 vma->vm_start == vma->vm_pgoff << PAGE_SHIFT 所对应的物理地址
   ⇒ 实现"物理 X ↔ 虚拟 X"的恒等映射
3) 若 App 的 mmap 请求带 hint/ MAP_FIXED，就严格按它给的地址映射
```

**判据**：修好后 App 在 `0x085360E4` 的写不再 trap；日志里应能看到
"identity map phys 0x08000000-0x0C000000 → va 0x08000000-0x0C000000"。

## 五、一条便宜的确认实验（建议先做）

在 `fake_mmap` / `fake_open` 里把 **App 请求的参数**打全：

```
va 请求值（vma->vm_start / mmap 的 addr 参数）
vma->vm_pgoff（偏移，通常决定要映射哪段物理）
是否有 MAP_FIXED
```

- 若 App 传了 `addr=0x085360E4` 附近的 hint 或 `MAP_FIXED` ⇒ **立刻确认恒等映射假设**
- 若 App 从没请求过该区间 ⇒ 那它是从**另一个 ioctl** 拿到/算出的，去追那个 ioctl 的返回值

## 六、和前面几轮的关系

| 崩溃 | 性质 |

| MonDrv / dmp_allocator:108 / alloc_sync:169 | **缺服务**（模块被 stub）→ 恢复真模块已解决 |
