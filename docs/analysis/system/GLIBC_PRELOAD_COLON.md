# glibc 2.11.2 的 LD_PRELOAD 解析：冒号可用，失败不致命

> 问题：真机侧要往 `LD_PRELOAD` 里塞多个库（`.so:A.so:B.so`），
> 但不确定 glibc 2.11.2 是否支持冒号分隔，以及单条失败会不会导致启动失败。

**证据来源**：ZV-E10 `/rootfs/lib/ld-2.11.2.so`（101,736 B），直接读 `.rodata`。

## 一、★ 证据一：分隔符字面量 `" :"` 紧挨在 `"LD_PRELOAD"` 之后

```
.rodata  va=0x13368  size=0x37C4

@va=0x14718 上下文（原始字节）：
  ... "LD_PRELOAD\0\0 :\0\0: \t\n\0\0\0\0i ==" ...
             ↑        ↑
         LD_PRELOAD   " :"
```

**⇒ 编译器把 `"LD_PRELOAD"` 与 `" :"` 相邻放置（同一段代码的两个常量）。
对应 glibc `elf/rtld.c`：**

```c
while ((p = strsep (&list, " :")) != NULL)   /* 空格与冒号都是分隔符 */
```

## 二、★ 证据二：单条失败只警告、不中止

**同一 `.rodata` 里有完整错误串：**

```
ERROR: ld.so: object '%s' from %s cannot be preloaded: ignored.
                                                ↑↑↑↑↑↑↑↑
```

**⇒ `ignored` 表明该条目被跳过、继续处理后续条目。**

**⇒ preload 条目失败（文件不存在 / 无法加载）不会导致进程启动失败。**

## 三、结论

| 问题 | 答案 |
|---|---|
| 支持冒号分隔吗？ | ✅ **支持**（与空格同为分隔符）|
| 单条失败会中止启动吗？ | ✅ **不会**，打印警告后继续 |
| 多条 preload 可用吗？ | ✅ 可用 |

**⇒ 真机侧可走「三条目」方案，同时获得新菜单 + 模块系统 + 自愈：**
```
/usr/tool/libefence.so:/setting/zvegisk/zvegisk.so:/log/zvegisk/m2/libIMDB.so
```

**⇒ 补丁版 libIMDB 转为兜底方案（万一白名单校验比静态分析更严）。**

## 四、真机验证的判据（比静态分析更可靠）

**实验配置：**
```
/usr/tool/libefence.so:/usr/lib/libnosuch.so:/usr/lib/libm.so.6
```

**判据看「报了几条 `cannot be preloaded`」：**

| 现象 | 含义 |
|---|---|
| 报 **2 条** | ✅ 冒号被正确解析（两条分别失败）|
| 只报 **1 条** | ❌ 整串被当作一个路径，冒号未解析 |
| `libm.so.6` 不报错 | ✅ 单条失败不影响其余 |
| 相机正常启动 | ✅ 失败路径无害 |

**⚠️ 注意：`libm.so.6` 本来就会被后续加载，它不报错不能单独证明什么，
真正判据是「2 条 vs 1 条」。**

**⚠️ 失败模式是"新菜单没生效、相机仍正常启动"，不是变砖。**

## 五、方法论备注

**本次尝试用自写的 Thumb `adr` 扫描器找代码引用点，未命中 ——
因为 ld.so 是 PIC 代码，字符串寻址可能走 GOT 或其它形式，且我的手写解码器
在本项目中已有多次出错记录。**

**⇒ 结论不依赖那个扫描器：`.rodata` 里的字面量 + 错误串是【直接观测】，
不是推断。但「代码里确实调用了 strsep」这一点仍是基于 glibc 源码知识的推断，
最终应由真机实验（报 2 条 vs 1 条）确认。**
