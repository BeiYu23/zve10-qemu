# 崩点偏移的精确结构：48 × 128KB

## 一、分解结果

```
0x6000E4 = 48 × 0x20000 + 0xE4        （48 个 128KB 块 + 228 字节）
```

## 二、两个案例的块索引（完全一致）

| 窗口 | 窗口块数 | 访问的块 | 越过窗口 |
|---|---:|---:|---:|
| 16 MB | 128 | **176** | **+48 块** |
| 32 MB | 256 | **304** | **+48 块** |

**⇒ 两种配置下，App 访问的块索引都恰好等于 `窗口块数 + 48`。**

## 三、含义

1. App 的地址算术**以 128KB 为粒度**（`base + i × 0x20000`），
   与 `grm_gles.ko` 的 `0x20000` 契约完全吻合 ✓
2. App 要的是**窗口之后第 48 块**
3. 48 × 128KB = 6 MB —— 这就是那个"神秘 6MB"的真身：
   **它不是大小，是 48 个块**

## 四、推论

App 认为窗口之后**还有 48 块可用**。也就是它期望的总量是 `窗口块数 + 48`，
而不是窗口块数本身。

⇒ 这与 `grm_gles.ko` 的真实契约矛盾：真驱动每次只给 128KB，
App 必然通过**多次 mmap** 累积到需要的块数。

⇒ QEMU 侧"一次给一大片窗口"的模型，**在块索引 48 之后必然越界**，
与窗口开多大无关 —— 因为 App 的坐标原点是"窗口块数"，不是"我拿到的内存量"。
