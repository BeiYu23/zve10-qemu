# 相机调试最佳实践（ZV-E10 实战总结）

> 来自 2026-10-22 ~ 10-29 的真实实践。每条都对应一次成功或一次事故。
> 适用：任何"只能靠设备自身表现判断"的嵌入式调试。

---

## 一、通道分层：永远按可靠性从高到低选

```
第 0 层  BootROM / Pico 注入 → fastboot     内核崩了也能用   ★最后保险
第 1 层  USB gadget + 后台守护进程           内核活着就能用   ★日常主力
第 2 层  服务模式 Jiritsu（0x0336）          相机能正常启动
第 3 层  WiFi / agent TCP                   应用层起来才可用
第 4 层  屏幕观察                             最差，只能看现象
```

**原则：能用第 1 层就不要用第 2 层；需要"设备完全不动"时才用第 0 层。**

**教训**：10-28 我们只有第 4 层（屏幕），结果排查一整晚方向全错。

---

## 二、五条验证铁律（每条都有血案）

### 1. 采样 ≠ 验证，必须全量

**事故**：10-28 刷 nflasha10 后"3 个采样点 all match"就宣布修好，实际只有前 768 KiB 写进去。
**做法**：`verify_partition.py` 逐块比对，必须 `RESULT: 0 mismatching blocks`。

### 2. 验证必须用"会被修改的区域"

**事故**：10-28 用从未改动的扇区比对，结论是"完全一致"，等于什么都没验证。
**做法**：验证的地址必须是**你刚刚写过的那一段**。

### 3. 写入成功 ≠ 生效

**事故**：
- `--reference` 与 `--image` 同文件 → 0 字节写入，却报"完成"
- Jiritsu 写 `/setting/x` 实际落在 `/tmp/jiritsu/setting/x`（路径沙盒），读回还一致

**做法**：
- 写完**从另一个视角**确认（shell 的 `ls`/`cat`，不是写它的那个工具）
- 怀疑"到底写没写"时，用**独立通道**复查

### 4. 单变量原则

**做法**：一次只改一个东西，改完立刻验证。
**正面案例**：昨天把 M2 版 `libInfraMscServer.so` 单独换进原厂 `/usr`，USB 正常 ⇒ 干净地排除了一个候选。
**反面案例**：同时刷 nflasha10 + nflasha2，无法判断哪个是疗效来源。

### 5. 阳性对照：先证明"工具能工作"

**事故**：LD_DEBUG 若没生效，会以为是"v9b 起不来"，实际是探测手段没跑起来。
**做法**：任何探测手段，先在一个**已知正常**的场景验证它真的输出，再拿去测故障场景。

## 三、危险操作黑名单

| 操作 | 后果 | 替代做法 |
|---|---|---|
| 写 `/etc/ld.so.preload` | glibc 2.11.2 加载失败即**全系统 exec 崩** → 3 秒重启循环 | `/setting/env.txt`（见 playbook §9） |
| 往分区偏移 0 写数据 | 10-27 测速事故：毁 FAT 引导扇区 → 整机重启循环 | 写到分区**末尾**或读-改-写同一块 |
| `--reference` 指向与 `--image` 相同的文件 | 0 字节写入的"假修复" | 不传 `--reference`，用 `--full` |
| `STOP_SENSER`（Jiritsu `stop()`） | 相机 USB 设备被摘除 | 不调 stop，让它超时自己回 `0x0d95` |
| 同时改两个以上变量 | 无法归因 | 单变量，一次一个 |
| 相信"出厂镜像" | 10-28 的 `nflasha2_factory.img` 的 `dmode` 缺换行，刷了就是 UI 出来但 3 秒重启 | 用之前逐字段验（dmode 必须 2 字节 `"3\n"`） |

## 四、标准调试流程（只读 → 小写 → 大写）

```
① 只读诊断
   读超级块 / 分区表 / 关键文件 / 进程 / 挂载 / environ
   ← 这一步不能造成任何改变

② 单点小写 + 立即验证
   改一个字节/一个文件 → 用独立通道确认 → 不行就回滚

③ 大改（刷分区 / 换库）
   前提：①② 全部建立，且有完整备份和明确回滚路径
```

**反例**：直接刷 `/usr`（第 ③ 步）却没有第 ① 步的基线，导致"无 UI"后无法判断是刷写问题还是移植问题。

## 五、必须能识别三类假象

### 1. 假阳性（以为成功，其实没做）
- `0.0 MiB written` 却报"finished"
- 采样点恰好在未改动区域
- 写入被沙盒化，读回也是沙盒

### 2. 假阴性（以为失败，其实做了）
- 探测手段自己没生效（LD_DEBUG 未写成功 → 没有日志 → 误判"目标没问题"）
- 校验读错地址 → 假 MISMATCH（`--part-start` 缺失时害了我们两次）
- 路径未挂载 → `LD_PRELOAD` 静默失败

### 3. 症状重名（不同病因，同一表现）
- 「3 秒重启」可能来自：`ld.so.preload` 坏 / `dmode` 缺换行 / 内核 panic
- 「无 UI」可能来自：`/usr` 没挂 / appFw 加载失败 / 应用层等 IPC

**⇒ 同名症状必须先做**分层定位**（内核活否 → init 活否 → bootin 活否 → 应用活否），不要直接猜。**

## 六、每次实验前必须写下三件事

```
1. 我改了什么（精确到文件/字节）
2. 我怎么验证（用什么工具、看什么输出、什么算成功）
3. 我怎么回滚（具体命令、备份在哪）
```

**写不出来的，就不要做。**

---

## 七、记录与知识沉淀

- **每次改动都落文档**，尤其是失败尝试 —— 排除了什么，比做成了什么更有价值
- **playbook 要能照着执行**：命令、参数、判据、失败模式，四件齐全
- **镜像/备份标可信度**：哪些是原厂、哪些含自己的调试残留、哪些已废
- 关键结论标注**证据等级**：反汇编确认 > 实测 > 推测

---

## 八、当前项目的最优起手式（结合现状）

```
第 1 步：相机正常启动 → 用第 2 层（服务模式）拿 shell，收集基线
第 2 步：把第 1 层（gadget + 守护进程）写进 bootin 包装脚本并验证
         ← 此后所有实验都有"内核活着即可用"的通道
第 3 步：再动 /usr（刷 v9b）
         ← 因为崩了也能进第 1 层，不再是"盲刷"
```

**核心思想：先建立观察能力，再做改变。**
