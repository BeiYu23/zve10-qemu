# `zvegisk.so` 失效模式分析（这个 .so 坏了会怎样）

> 用户问：「你再次检查一下整个 so，这个 so 损坏/崩溃会怎么样？」
> 答案：**最坏情况是「相机会忽略它、正常启动」** —— 但有几处必须知道的具体风险。

---

## 一、★★★ 为什么它坏不了相机：结构上的保证

### ① 零依赖（不可能因符号解析失败）

```
未定义符号数: 0
NEEDED: 无
⇒ 不依赖任何库、不引用任何外部符号
⇒ 加载时只需要 ld.so 能读 ELF 头
```

### ② 构造函数的父进程路径**只有一个调用**

```c
__attribute__((constructor)) static void zvegisk_init(void)
{
    int pid = sy0(SYS_fork);   // ← 父进程路径只有这一个 syscall
    if (pid == 0) {
        work();               // 所有工作都在子进程
        sy1(SYS_exit, 0);
        for(;;){}
    }
    /* 父进程立刻返回 */
}
```

**⇒ 父进程（im.elf）路径：`fork` → 判断 → 返回。**
**⇒ **零阻塞、零 I/O、零可能挂住的操作** ⇒ im.elf 的 main() 一定照常执行。**

### ③ `fork` 失败也是安全的

```c
int pid = sy0(SYS_fork);   // 失败返回 -1
if (pid == 0) { ... }      // -1 ≠ 0 ⇒ 走父进程 ⇒ 直接返回
```

### ④ init_array 正确注册（已验证）

```
.init_array  vaddr=0x11F7C  size=4
entry = 0x494  ==  zvegisk_init 的地址  ✓
```

### ⑤ 段对齐正确（已验证）

```
LOAD off=0x1F7C  vaddr=0x11F7C  → 差 0x10000 ✓
（a7c2 记录过：错位会被 SIGKILL）
```

## 二、逐条失效场景

| # | 场景 | 后果 | 结论 |
|---|---|---|---|
| **1** | **.so 文件损坏**（上传不全/位翻转）| **ld.so 加载失败 → 打印警告 → im.elf 正常启动** | ✅ **最安全** |
| **2** | **构造函数崩溃** | **父进程已 fork 并返回 ⇒ im.elf 继续** | ✅ |
| **3** | **fork 失败** | **走父进程路径，直接返回** | ✅ |
| **4** | **子进程崩溃** | **只死子进程，im.elf 无恙** | ✅ |
| **5** | **子进程 hang**（mount 卡住）| **im.elf 已继续，UI 正常；但子进程可能持有 mount** | ⚠️ 见下 |
| **6** | **mount_sd 部分失败** | **可能残留 /tmp/zdev tmpfs（RAM，无害）** | ✅ |
| **7** | **写 /setting 失败**（满了/目录不存在）| **计数不生效 ⇒ 保护机制失效，但无副作用** | ⚠️ 见下 |
| **8** | **boot_count 达阈值** | **建 safemode，之后永不动作** | ✅ 设计如此 |
| **9** | **watchdog 误触发** | **已加 `armed` 开关 ⇒ 测试时不启动** | ✅ 已修 |
| **10** | **Phase 2 绑了坏文件** | **App 崩 → 无 UI → watchdog 90s 后 umount + reboot → boot_count++ → 3 次后 safemode** | ⚠️ **最终自愈** |

## 三、⚠️ 三个必须知道的具体风险

### 风险 A：SD 卡挂载冲突（**已修**）

**vfat 不支持多重挂载冲突场景：**
- **多重**读写**挂载：第二个直接 EINVAL**
- **一个读写 + 一个只读：读写那个会 EBUSY**

**⇒ 我们如果挂着 SD 不放，相机自己就无法录制/回放。**

**★ 修法：**
```c
mount(..., MS_RDONLY, 0);   // 只读挂
read boot_mode;
unmount_sd();               // ★ 读完立刻卸载，窗口毫秒级
```

### 风险 B：`boot_count` 会被测试消耗

**每次 dlopen 就会 `boot_count++`。
⇒ 测试 4 次就触发 safemode（我们实测确认了）。**

**★ 部署前必须：`echo 0 > /setting/zvegisk/boot_count; rm -f safemode`**

### 风险 C：子进程 hang 会留下 mount

**如果 mount 卡住（坏卡/慢卡），子进程会一直挂着，且持有 /tmp/zdev 的 tmpfs。**
**⇒ 对相机**无直接危害**（tmpfs 在 RAM 里），但会占一点内存。**

**★ 缓解：Phase 1 的 mount 窗口极短（毫秒级）。**

## 四、★★★ 真正的最坏情况

**如果 .so 在**父进程路径**上崩了（即 fork 之前）—— 那 im.elf 直接死，无 UI。**

**⇒ 但 fork 是第一条语句，之前只有函数序言（压栈/减栈指针），
**除非 ELF 加载本身有问题，否则不可能崩。**

**★ 而 ELF 加载失败的情况（场景 1）是**非致命**的 —— ld.so 打警告后继续。**

**⇒ 所以理论上不存在"加载这个 .so 导致相机起不来"的路径。**

---

## 五、⚠️ 但我必须诚实说明一个前提

**以上所有安全性，都建立在「通过 `/setting/mode/preload` + `dmode=3p` 加载」这个前提下。**

**如果换成之前那条 `/etc/ld.so.preload` 的路，**就没有任何保证** ——
那条是动态加载器对**所有进程**生效，坏库会让 init 都起不来（当初变砖就是这个）。**

**★★★ 两条路径的本质区别就在这里。**
