# GPU 耦合问题：实测证据 + 我方错误纠正

## 一、我方错误：`"无 libgrm ⇒ 无 GPU 库-驱动耦合"` **不成立**

**实测（两版 libObj 对照）：**

| 项 | ZV-E10 libObj | ZV-1M2 libObj |
|---|---:|---:|
| 大小 | 21,305,528 | 3,931,624 |
| `/dev/dmpgles2` 引用 | 1 | 1 |
| `"GRM_"` 相关字符串 | 60 | 58 |
| `GraphicsEngine`/`uxengine` | 22 | 25 |

**⇒ 用户态 GPU 客户端就在 libObj 内部。**
**我把"没有独立的 `libgrm.so` 文件"错误等同于"没有 GPU 客户端代码" —— 偷换概念。**

## 二、★ 但这条风险可用实测关闭：两个 `.ko` **除 build-id 外完全相同**

**`grm_gles.ko`（15,648 B）逐字节对比：**

```
差异: 20 字节，仅 1 段: 0x02458-0x0246B
该偏移落在 .note.gnu.build-id (fo=0x2448, 段内偏移 0x10)

E10: f47e3146365cb30422409c929aa3899424e09738
M2 : 960283866a105355b819e712d5cab76e4c456c46
⇒ 20 字节 = SHA-1，链接器生成的构建 ID
```

**`grm_ma.ko`（24,800 B）同样：仅差 20 字节，同位置。**

**`vermagic` 两版相同：**
```
3.0.27_nl-rt106+ SMP preempt mod_unload ARMv7
```

**⇒ 已比对的两个 `.ko` 文件逐字节内容仅在 `.note.gnu.build-id` 的 20 字节上不同，
两者 `vermagic` 相同。**

**⚠️ 边界（对方明确要求，不得提升）：**

```
✅ 可以说：缩小了"驱动实现版本差异"的不确定性
❌ 不可以说：客户端↔驱动耦合风险已关闭
❌ 不可以说：ABI 不匹配已完全排除
```

**⇒ 未覆盖的方面仍包括：**
```
· libObj 实际调用参数（不只是命令号，还有参数结构与调用上下文）
· DMM / UDIF 依赖
· 运行时配置（加载参数、内存预留、设备树）
· 初始化顺序
```

## 三、⚠️ 该条只部分关闭 —— 严格边界声明

**已证明：内核驱动侧相同。未闭合并列：**

**① 模块运行时配置可能不同**
```
.ko 相同 ≠ 加载参数 / 内存预留 / 设备树相同
例：grm_gles 的 vmalloc 环大小、dmm 预留区
⇒ M2 客户端按 M2 预期算出的地址/大小，可能与 E10 实际配置不符
⇒ 需真机 /proc 或 dmesg 才能确认
```

**② M2 客户端是否使用 E10 客户端不用的 ioctl**
```
.ko 相同 ⇒ 支持的 ioctl 集合相同 ⇒ 不会"找不到命令"
但行为/返回结构若有版本分支，仍可能不匹配 ⇒ 只能实测
```

**⇒ 准确表述：**
> **驱动二进制相同（除 build-id）⇒ 无驱动 ABI 版本不匹配；
> 但运行时配置与客户端 ioctl 用法是否匹配，仍未验证。**

## 五、错误归类（三条同类）

**本次审计暴露的我方错误中，有 3 条属同一类：**

```
1. mount 第 5 参按 C 约定传栈（应 r4）
2. 尾调用用绝对 vaddr（忽略 ET_DYN load bias）
3. "无 libgrm ⇒ 无 GPU 耦合"（偷换概念）
```

**共同点：**
> **用"看起来合理"的推理代替"对照实际 ABI / 二进制"。**
