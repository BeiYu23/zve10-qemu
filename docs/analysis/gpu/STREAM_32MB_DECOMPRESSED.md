# 0x20312000 的 32MB 区域：描述符 + 压缩帧数据（无原始像素）

## 一、分块快照结果

**块 #0（前 64KB）= 描述符表：**
```
+0x0004  0x000001e3   (483)
+0x0008  0x00000008   (8)
+0x0018  0x80312000   (自指，环基址)
+0x0024  0xffffffff   (sentinel)
+0x0028  0xffffdadd
+0x002c  0x35f92838   (校验/魔数)
+0x0038..  成对重复指针 (0x80312030, 0x80312038, ...)
```

**块 #1-#9 = 数据区，特征是**重复的 16 位模式**：**
```
块#1  +0x04=0x222f222f  +0x08=0x222f222f  +0x2c=0x222f222f
块#4  +0x04=0x000f000f
块#5  +0x04=0xa40fa40f  +0x08=0xb40fa40f
块#6  +0x04=0x111f111f
块#7-9 +0x04=0x000f000f
```

**★★★ `0x222F222F` = 重复的 16 位值 0x222F —— 这是**压缩流的重复标记**，
不是像素（RGB565 解出来是暗色，YUYV 解出来是绿屏）。**

## 二、所有尝试过的解码

| 格式 | 结果 |
|---|---|
| RGB565 @ 640×480 | 78 色但图像是密集横纹噪声 |
| RGB565 @ 4096 / 2048 / 1280 | 重复竖带 + 横纹 |
| **YUYV422** | **绿屏 + 噪声**（典型误判）|
| NV12 | 同样不是图像 |

**⇒ 不是任何一种原始像素格式。**

## 三、结论

**0x20312000 的 32MB 布局：**
```
块 #0       描述符/命令表（483 + 指针数组）
块 #1-#9    压缩帧数据（wbi_cmpr）
块 #37-#41  另一块结构（+0x04=0x3f800000 等，像 float 1.0 参数）
```

**⇒ CPU 侧**确实没有原始像素面**。这与 QEMU 那边的独立结论一致
（他们 GDB 直读物理内存确认 QEMU 里该区域从未被写过）。**

## 四、⇒ 要在真机上"画东西"，只剩三条路

| 路线 | 说明 | 难度 |
|---|---|---|
| **① 向命令环提交绘制命令** | 需要完全解描述符格式 | 高（但已被证明是唯一"原生"路径）|
| **② 用户态拦截 App 的绘制 API** | hook `GRM_gpermFillrect/Rectblit`，自己光栅化 | 中（QEMU 线正在做）|
| **③ 实现 wbi_cmpr 压缩** | 自己压缩一帧塞进压缩流 | 极高（格式未知）|

**★★★ 贪吃蛇（A7M3 同代 SoC）最可能是路线 ②：拦截绘制 API，
用自己的光栅化器画，不碰硬件命令环。**
