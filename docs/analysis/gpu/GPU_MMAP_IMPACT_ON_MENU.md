# `/dev/dmpgles2` mmap 发现对自绘启动菜单的影响

## 一、直接影响：决定"能不能画"

| mmap 结果 | 意义 |
|---|---|
| **映射到可写帧缓冲** | ✅ 能画 —— 可用像素直接画 |
| **映射到 GPU 命令区** | ⚠️ 能画但要提交 GPU 命令 |
| **映射为空/失败** | ❌ 回到"只能换资源" |

## 二、即使 mmap 成功，还有两个拦路虎

### 拦路虎 1：输入不可读

```
/dev/input/event*   = ENODEV（实测）
input.ko            = Sony 私有 udif 框架
APPFWINFRA_INPUT_GETEVENT = libObj 内部 API
```
**⇒ 无法做"可选的菜单"**

### 拦路虎 2：时序（更本质）

```
bootin → LD_PRELOAD 加载我们的 .so → 构造函数运行
                                          ↓
                              此时显示初始化了吗？
                                          ↓
                              im.elf 的 main() 才刚开始
```

**★ 如果显示是 im.elf 在 main() 里初始化的，
构造函数运行时显示还没就绪 ⇒ 画不进去。**

**⇒ 所以即使能画，也只能"UI 起来之后叠加"，不能"UI 之前画"。**

## 三、三种现实形态

### 形态 1：启动后叠加菜单（mmap 成功时）
```
im.elf 正常启动 → 显示就绪
  ↓
我们的守护进程：等 UI 起来 → mmap → 画菜单 → …
```
**⚠️ 输入仍是问题**

### 形态 2：★ 静态状态显示（不需要输入）—— 唯一完全可行的自绘形态
```
开机 → 显示一张我们画的图：
┌──────────────────────┐
│  zvegisk             │
│  MODE: NEW           │
│  boot_count: 1/3     │
└──────────────────────┘
```
**★ 不需要任何输入，信息价值高（用户能看到当前状态）**

### 形态 3：换资源（mmap 失败时的退路）
**回到策略 C：换 `color_cmn.uxc` 等，用 Sony 渲染器画**

## 四、结论：补上了最后一块拼图

**现在缺的：**

| 项 | 状态 |
|---|---|
| 崩溃回退机制 | ✅ 已实现验证 |
| SD 卡读取配置 | ✅ 已实现验证 |
| preload 钩子 | ✅ 机制已确认 |
| 资源格式兼容 | ✅ 已确认（76 个同名文件）|
| **可视化反馈** | ❌ 现在只能看日志 → **mmap 成功后可变 ✅** |
| **交互选择** | ❌ 只能改配置文件 |

**★★★ mmap 成功 = "能看到当前状态"这一项目闭环。
但"交互选择"仍需输入 RE。**

## 五、交互选择的其他途径（不解决输入时）

```
① 改 /setting/zvegisk/boot_mode（agent / USB）
② 改 SD 卡文件（拔卡插电脑）
③ 定时自动：开机 N 秒后按默认模式 —— 但"无操作"判断也要输入
```
