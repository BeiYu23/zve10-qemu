## 一、目标与判据

目标：让 ZV-E10（CXD90045，ARMv7，glibc 2.11.2）原厂 `/usr` 里的 App，
在自制 QEMU 机型上**由它自己绘制**并显示老菜单。

判据（必须同时满足，且不可伪造）：

| # | 判据 | 当前 |
|---|---|---|
| 1 | App 调用自己的绘制入口 `GRM_bitmapCreate` / `GRM_gpermFillrect`（定义在 libObj 内） | **否**（GDB 断点零命中） |
| 2 | 打开并驱动图形设备 `/dev/dmpgles2` | **否**（`FAKEGLES open=0`） |
| 3 | `/dev/stream@0x20312000` 由均匀 `0x5A5A` 变为非均匀 | **否** |
| 4 | 显示端呈现像素，且一次真实输入引起变化 | **否** |

## 二、方法论：为什么这份结论值得相信

这一阶段最大的教训不是"难"，而是**前期的很多"进展"其实是测量错误**。因此本轮固定了几条纪律：

1. **固定时长**而不是 idle 判稳。此前一次 43 秒的"零崩溃"被误当成修好，
   而真实崩溃点在 60 秒之后。
2. **替换文件必须读回校验**。镜像构造脚本对每个替换文件做 SHA-256 读回比对，
   分区做 `e2fsck -n`；不使用"命令返回 0"作为证据。
3. **区分原厂件、派生件、生成桩**。曾把本机 GCC 6.4 生成的桩库当作"从固件补回的原厂库"，
   并据此得出过安全结论——这些结论已全部撤回。
4. **否定结论同样入档**。每一条被否证的假设都写清了依据，避免重复劳动。
5. **对照实验**。例如"缺 33 个库"这一假设，用真机 `nflasha15` 解包树对照后被否定
   （真机同样没有这些库）。

## 三、已经站得住的东西

| 能力 | 证据 | 备注 |
|---|---|---|
| 自制机型 `cxd90045` 的 DDR 布局与内核 cmdline 完全一致 | `mem=1G@0`、`mem=256M@0x80000000@1` 对应 DDR0/DDR1 | 之前的"内存不足"猜测不成立 |
| `bionz-streamfb` 能把 guest 物理 `0x20312000` 呈现为 QEMU 显示设备 | QMP `screendump` 可截帧 | 只是显示桥，不等于 App 画了东西 |
| **DMM（显示内存管理）协议实现** | 从 `grm_ma.ko` 反汇编得出完整契约 | 见下节 |
| **原厂 MA 服务确实在工作** | GDB 断 `ma_user_sync_cb` 抓到 `op=7/1/9/10/2/1/9×4` 序列 | 排除了"队列没人回"的猜测 |
| 原厂启动路径在修正 DMM 后**稳定 180 秒零崩溃** | 此前同路径约 60 秒随机崩在 ld.so | 见下节"旧悬案" |
| 原厂 App 线程体全文解出 | `ux 初始化 → 栈上构造 App → 投事件 → 主循环 → 析构` | 对象是线程栈局部变量，不是全局单例 |

### DMM 协议（本轮最有复用价值的成果）

从 `grm_ma.ko` 的 `ma_dmm_open_send_recv` / `ma_dmm_close_send_recv` 反汇编得到：

| | open（op=1） | close（op=4） |
|---|---|---|
| 请求 `+0x00` | `1` | `4` |
| 请求 `+0x02` | — | handle |
| 请求 `+0x14` | seq | seq |
| 应答 `+0x00` | **必须 `0x8001`** | **必须 `0x8004`** |
| 应答 `+0x04` | 单元索引 | — |
| 应答 `+0x06` | seq | seq |
| 应答 `+0x10` | 物理基址 | — |
| 应答 `+0x14` | 长度 | — |

此前我们把所有应答硬编成 `0x8001`，于是 close 校验必然失败，触发
`grm_ma` 自己的 `BUG_ON`（`dmm_if.c:281`）。按上表实现后，BUG 消失，
App 拿到了**正确的 32MB 图形池**（`QMMAP len=0x2000000 off=0x20312000`）。

### 一个旧悬案的合理解释

早期记录里"不确定的 ld.so 崩溃"（三个不同偏移、全是空指针）很可能**由我们自己造成**：
字段顺序错误的应答导致 `len=0x20312000` 的 512MB 映射，把 MA 空间放错位置、越界写破坏加载器
地址空间。修正后同路径不再复现。这一条按**假说**记录——缺"故意改回旧字段再崩一次"的对照。

## 四、当前的确切阻塞链

1. **UX 初始化执行中撞在未初始化的单例上。**
   早先观察到"崩在 libc 的 Thumb syscall 蹦床（非法指令）"，但后来实测**线程栈大小会改变
   失败点**（默认栈→非法指令；1 MB→`libObj+0x63d240` 的 NULL；4 MB→`p4` 为 NULL），
   因此"Thumb 态丢失"的解释**降级为未证实**，更可能是栈溢出破坏返回链。原始描述如下：
   `trap_no=6`（内核里明确是"非法指令"），故障地址 `0x04042796` 是**偶数**，
   而该处字节 `80 bd` 是 Thumb 的 `pop {r7,pc}` —— 即这段 Thumb 代码被以 **ARM 态**取指，
   某个间接调用或返回丢了 Thumb 位。
   已排除：内核缺 Thumb 支持（`CONFIG_ARM_THUMB=y`、hwcap 正常）、
   宿主用 ARM 还是 Thumb 编译（两种都崩）、我们自己的拦截层（移除后崩溃不变）。

2. **App 主体初始化需要一个 `libObj+0x145CBC4` 指针，而它在本镜像中没有任何写者。**
   已穷举：字面量池 / `movw-movt` / 基址+偏移三种寻址写法；预置硬件写监视（含库加载与
   构造期）；原厂路径跑 110 秒——**都没有任何代码写它**。21 处计算该地址的站点全是"读蹦床"。

3. 两者构成闭环：初始化要先跑完才能产生 `p4`，而初始化在到达那一步之前就崩了。

## 五、已否证的假设（省得别人重走）

| 假设 | 结论 |
|---|---|
| 13 个"补回的库"是原厂文件 | 否，全是本机 GCC 6.4 生成的桩 |
| `ld.so+0xA706` 是 `DT_INIT_ARRAY` 处理 | 否，是 PLT 符号解析路径 |
| 加载器崩溃源于固件堆损坏 | 未证实；修正 DMM 后不再崩 |
| 缺 33 个 `MISSSO` 库 | 不需要，真机也没有 |
| 崩在用户态 `osal_rcv_msg_tmo` | 否，命中内核同名函数 |
| `p4` 有写者 | 无（三种寻址 + 写监视 + 原厂路径都没抓到） |
| 所有引擎单例都未创建 | 部分错：`GraphicsEngine` 是静态对象，一直存在 |
| 单例可由我们手动创建 | 否，创建函数互相依赖成环 |
| 状态字 `0x145ca6c` 被"污染" | 否，是初始化自己在入口置的（写监视抓到 `0x610f9c`） |
| 我们的信号量拦截层导致崩溃 | 否，移除后崩溃完全相同 |

## 六、如果要继续

按信息增益排序：

1. **定位 Thumb 位丢失点**（最关键）。建议在内核侧记录 `regs->ARM_cpsr & PSR_T_BIT`
   在 `ret_to_user` / 信号返回 / 可疑 `blx` 处是否翻转。
   注意：**不能在 syscall 热点蹦床上下 GDB 断点**（会把 guest 拖死，已实测）。
2. **确认 `p4` 的解释**：它由我们未加载的组件设置，还是这族蹦床在本机型配置下是死代码。
   这需要到未加载的固件组件里做新一层逆向，与已有证据链不是一个课题。
3. 上述任一项突破后，才轮到绘制侧（`GRM_*` → `/dev/dmpgles2` → streamfb 提交）。
