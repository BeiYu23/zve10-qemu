# `.uxc` 格式语法（反推结果，离线验证）

> 目的：为"新引擎 + ZV-E10 老内容"的适配提供可操作的格式知识。

---

## 一、`.uxc` 容器语法（已在 4 个文件上验证）

```
偏移   类型      含义
─────────────────────────────────────────────────────────────
0x00   char[4]   magic = "uxc\x07"            （两版相同）
0x04   u32       version = 0                  （两版相同）
0x08   u16       type                         （仅两种：0x08 / 0x0F）
0x0A   u16       resource_id                  （每文件不同，如 color=0x4A）
0x0C   4 bytes   未完全解出；与条目数量相关    （color: 0x23/0x2E，style: 0xC03C/0xE03E）
0x10   u16[]     偏移表：table[i] = 第 i 条的偏移（相对数据区起点）
                 0xFFFF = 该槽位为空（color_cmn 有空槽）
data   ...       N 个条目（大小按资源而定）
```

### 1.1 `type` 字段：**只有两种，两版完全相同**

| type | 数量 (E10/F) | 含义 | 例 |
|---|---|---|---|
| **0x08** | 251 / 113 | 通用数据资源 | `IRShooting.uxc`、`LayoutMaster_Menu.uxc`、`color_cmn` |
| **0x0F** | 40 / 33 | 字符串资源 | `string_arabic_f.uxc` |

**⇒ ZV-E10 的 type 集合 ⊆ ZV-1F 的 type 集合（完全相同）。**

### 1.2 偏移表：**自描述**

引擎按 `table[i]` 定位条目 ⇒ **不需要知道条目数量以外的东西**。
`0xFFFF` 表示空槽（`color_cmn` 里就有 8 个空槽）。

**⇒ 这是换资源能成立的根本原因：数据是自描述的，引擎按表读。**

## 二、四个叶子资源的实测解码

| 文件 | type | id | 偏移表 N | 条目大小 | E10 / F 大小 |
|---|---:|---:|---:|---|---|
| `color_cmn.uxc` | 0x08 | 0x4A | **36 槽（28 用）** | **8 B 定长** | 312 / 388 |
| `style_cmn.uxc` | 0x08 | 0x3D | **61** | **9 B 步长** | 1,888 / 1,940 |
| `lang_cmn.uxc` | 0x08 | 0x33 | **47** | **变长（≈5）** | 1,048 / 1,048 |
| `lang.uxb` | — | — | — | — | 2,896 / 2,896 |

### 2.1 `color_cmn.uxc` 完整解码

```
0x00  "uxc\x07"  ver=0  type=0x08  id=0x4A
0x10  36 个 u16 槽位（0xFFFF=空）
0x58  28 条 × 8 字节 = 224 B  →  0x58+224 = 0x138 = 312 ✅ 完全吻合
     每条: [u8 序号][40 09 3a][R][G][B][A]
     例: [00] 40093a 000000FF = 纯黑不透明
         [01] 40093a DDDDDDFF = 浅灰
         [02] 40093a 00000099 = 黑 60% alpha
```

**ZV-1F 版：46 槽、35 条 → 0x6C + 35×8 = 0x184 = 388 ✅**

**⇒ 条目数 28 → 35，结构完全相同。**

### 2.2 `style_cmn.uxc` 解码

```
0x10  61 个 u16，步长 9（0, 9, 18, … 540）
      ⇒ 条目 9 字节步长，偏移落在地下数据区内
```

**两版前 56 字节（含表头 12 项）完全相同。**

### 2.3 ★ `lang_cmn.uxc` 与 `lang.uxb`：**两版字节完全相同**

```
lang_cmn.uxc  md5 dbae69e03c9c8662acd3ab4bb349021d  （两版一致）
lang.uxb      2,896 B，两版一致
```

## 三、★★ 试验顺序修正：**先用"字节完全相同"的文件测覆盖机制**

原计划第一步是 `color_cmn.uxc`（看颜色变化）。**但有一个更好的第一步：**

| 步骤 | 换什么 | 预期结果 | 这一测什么 |
|---|---|---|---|
| **0** | **`lang_cmn.uxc` + `lang.uxb`** | **★ 屏幕完全无变化** | **覆盖机制是否被正确应用** |
| 1 | `color_cmn.uxc`（312→388） | 界面颜色变化 | 叶子资源替换是否生效 |
| 2 | `style_cmn.uxc`（1888→1940） | 样式变化 | 同上，条目数不同 |
| 3 | 才考虑 view / global.xdb | — | 索引层（风险高） |

**★ 为什么第 0 步更好：**

```
换入的文件与原文件【字节相同】
⇒ 若屏幕有任何变化 ⇒ 说明覆盖机制把它挂到了错误的位置/时机
⇒ 这是覆盖机制的【阳性对照】
```

**⇒ 它把"机制错了"和"内容不兼容"两个失败原因分开了。**
**⇒ 否则第 1 步失败时，你无法判断是覆盖没生效，还是配色本身导致崩溃。**

## 四、适配可行性结论（格式层）

| 项 | 结论 |
|---|---|
| 容器头（magic/version） | ✅ 相同 |
| `type` 分类法 | ✅ **只有 2 种，两版完全相同** |
| 偏移表语法 | ✅ **自描述，引擎按表读** |
| 叶子资源（color/style/lang/string） | ✅ **可换**（`lang_*` 甚至字节相同） |
| `view*.uxc`（老菜单 291 个） | ⚠️ 格式同，但**是否被新引擎加载**取决于索引层 |
| `global.xdb` 索引方案 | ❌ **两版不同**（E10 索引 313 项含 view/master；ZV-1F 只索引 154 项） |

**⇒ 格式层没有需要"适配"的补丁；真正的分歧在【索引层】。**

---

## 五、`global.xdb` 的索引差异（已核实）

```
ZV-E10  引用名 313 个（含 214 个 view*.uxc + master_* + image_*）
ZV-1F   引用名 154 个（只有 image_* + string_*，【不含 view 也不含 master】）
共同引用 74 个（color/lang/string 等叶子资源）
```

**引用格式**：ZV-E10 用裸名（`viewBaseSeq.uxc`），ZV-1F 部分用相对路径（`../../../usr/share/app/image_00_43.uxc`）。

**⇒ `master_*` / `LayoutMaster_*` 在 ZV-1F 里【存在但不被 global.xdb 索引】**
**⇒ 推测：新引擎按硬编码名字加载这几个框架文件。**

**⇒ 这对"新引擎 + 老内容"是关键：如果新引擎硬编码加载 `LayoutMaster_Menu.uxc` 等，**
**而老内容里也正好有这些文件（确实有），那框架层就对得上。**
