# 轮次 25：preload 失败是安全的（实证）+ 六条安全属性汇总

## 一、要验证的风险

```
如果 /log 分区挂载失败、或 /log/bindm2.so 被误删/损坏，
而 glibc 因此【拒绝启动】im.elf，
那么相机就会完全没有界面 —— 比"没有新 UI"严重得多（需 fastboot 恢复）。

⇒ 必须确认：preload 失败到底是"致命"还是"忽略"
```

## 二、四个实验（本机实测）

| 实验 | 条件 | 输出 | 退出码 |
|---|---|---|---|
| 1 | `LD_PRELOAD` 指向不存在的文件 | `cannot open shared object file: **ignored**` | **0** |
| 2 | 指向损坏的 `.so`（非 ELF） | `file too short: **ignored**` | **0** |
| 3 | 列表里第二个不存在、第一个正常 | 只警告缺失那个 | **0** |
| 4 | 全部不存在 | 两个警告 | **0** |

**每种情况下程序都正常打印"程序正常运行"并返回 0。**

**⇒ glibc 对 LD_PRELOAD 失败只是打印 `ignored` 警告，不会阻止程序启动。**

**⇒ 即使 /log 挂载失败 / bindm2.so 缺失或损坏，im.elf 仍会启动，老菜单照常出现。**

**诚实边界：相机是 ld-2.11.2（老 glibc），本机是新版。
 但 `ignored` 这个行为从 glibc 2.3 起就是如此，几乎不可能有差异。**

## 三、构造函数本身的崩溃风险（静态评估）

```
栈帧           : sub sp, sp, #52        ⇒ 只有 52 字节，不会栈溢出
外部函数调用   : 0（未定义符号=0，全是裸 syscall）
静态缓冲       : 在 .bss（file_has 8192B / log_line 2048B / cmdline 512B）
失败路径检查   : 源码里 26 处"失败即返回/分支"的检查点
⇒ 不存在空指针解引用、越界写、递归、动态内存分配
⇒ 构造函数崩溃的概率极低
```

## 四、六条安全属性汇总

```
① preload 缺失/损坏 → glibc 忽略，程序照常启动            ★本轮实证
② bindm2 构造失败   → 只是不 bind，老菜单不受影响          （26 处失败检查）
③ bind 生效但 app 跑不通 → 重启即恢复（bind 不持久）       （设计保证）
④ 镜像损坏        → mount 失败 → 不 bind → 老菜单正常     （失败路径）
⑤ 上传中断        → 半截镜像不匹配 size 记录 → 自动重传   （第 21 轮实证）
⑥ 不写任何 flash   → 零持久改动                           （设计保证）
```

**⇒ 这条测试路径的最坏结果是"什么都没发生"，不可能是砖。**

## 五、与"刷机方案"的安全性对比

| | loop+bind（A） | fastboot 刷 /usr（B） |
|---|---|---|
| 最坏结果 | 没变化（重启恢复） | 分区写坏 → 需刷回工厂镜像 |
| 需要的恢复手段 | 重启 | Pico + fastboot + 工厂镜像 |
| 持久改动 | 无 | /usr 分区本体 |

**⇒ 这也是为什么建议先做 A：不仅零风险，而且能预测 B 的结果。**
