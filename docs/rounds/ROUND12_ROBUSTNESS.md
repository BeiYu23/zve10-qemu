# 轮次 12：appFw 启动壳分析 + 部署工具健壮性加固

## 一、反汇编 `appFw.so` 的 `Application_Start`

```
Application_Start @ 0x0054d580（只有 ~9 条有效指令）
  54d584: push {r7,lr}
  54d586: sub.w sp, sp, #2208      ← 在栈上分配一个 2208 字节对象
  54d590: blx 0x92559c             ← 内部函数
  54d59a: bl   0x54d154
  54d5a6: bl   0x54d2b0
  54d5ac: bl   0x54f664
  54d5b0: blx  0x923c84            ← 内部函数
  54d5b6: bl   0x54d538
  54d5be: pop {r7,pc}              ← ★ 直接返回，没有事件循环
```

**结论：**
```
Application_Start 是个"薄壳"：构造一个 2208 字节的对象、调几个初始化函数、然后返回。
真正的 UI 事件循环不在这里（大概率在 appFwBoot 建的线程里，或别处的主循环）。
⇒ 无法从入口判断它在哪一步卡住；appFw.so 去符号（除导出符号外无符号表），
  逆到能定位的程度需要大量工作，而且【无法修改】——边际价值低
⇒ 决定：不再深入 appFw 内部逆向，把精力放在提高明天一次成功率上
```

## 二、部署工具健壮性加固（两处）

### 2.1 `bindm2` 支持多路径查找镜像

```
原来只认 /log/m2usr.img
现在依次尝试：
    /log/m2usr.img   （500 MB 分区，默认）
    /sd/m2usr.img    （SD 卡，若有 58 GB 的卡插着，上传会快得多）
    /tmp/m2usr.img   （12 MB，只够放极小的测试镜像）
并在日志里记录 "image: <实际路径>"
```

**⇒ 若插了 SD 卡，可以直接把镜像拷到卡上，省掉 4~8 分钟的 WiFi 上传。**

### 2.2 上传断点续传

```
镜像 237.6 MB = 238 块 × 1 MB，WiFi 中途断了不能从头来

实现：每块追加成功后把「已提交字节数」写进 /log/m2usr.size
重启脚本时：
  · /log/m2usr.img 的实际大小 == 记录值  ⇒ 从对应块继续
  · 不一致（追加过程被打断）            ⇒ 删掉重来（避免半截镜像被挂载）
上传完成后删除 /log/m2usr.size
```
