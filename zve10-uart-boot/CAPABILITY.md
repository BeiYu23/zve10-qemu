# 当前能力评估（2026-10-22 下午）

## 一、已经具备的能力（实测确认）

| 能力 | 状态 | 说明 |
|---|---|---|
| 执行任意 ARM32 代码 | ✅ | 串口启动 → payload 执行（1 秒长闪验证） |
| 单次载荷 ≤ 约 6 KB | ✅ | 记录组 <1.45 s 限制 |
| 突破载荷限制 | ✅ | stage2 二级加载器：任意大小数据写入 SRAM |
| 数据完整性校验 | ✅ | 接收器 CRC32 + 长闪报告 |
| 传输进度可视 | ✅ | 每 32 KB 一个空档 → 相机闪一下 |
| 关闭看门狗 | ✅ | 0xF2402000/0xF2402004 |
| 相机 LED 控制 | ✅ | GPIO0 bit0 |
| 双载波模式 | ✅ | 记录用翻转、数据用空闲 |

## 二、当前做不到的

| 能力 | 阻塞点 |
|---|---|
| 读写 eMMC | SDHCI(MMCP) 初始化序列未解出，CMD0 超时 |
| 判定分区内容 | 同上 |
| 运行 Sony loader | 可加载 161 KB，但跳进去只会正常启动到内核（然后崩） |

## 三、这个环境下可以做的事（按可行性排序）

### A. 加载 Sony loader 并直接调用它的 eMMC 函数 ★推荐
```
· stage2 已能灌入任意大小数据（161 KB 可行）
· loader 内含完整 eMMC 初始化/读块/写后备 代码
· 需要：找到函数签名（r0/r1/r2 参数），从 loader 反汇编可确定
· 风险：调用约定未验证，可能要试几次
```

### B. 把 loader 的 eMMC 初始化"抄"进我们自己的 payload
```
· 已知 loader 的 0xfe04f746 初始化序列
· 已知 mmc_drv.ko 的寄存器偏移（0x00/0x04/0x06/0x08/0x0C/0x0E/0x24/0x58/0x2C/0x2E/0x3E/0x44FC/0x4204）
· 卡在：DMA 描述符格式、命令完成判定（PRESENT_STATE bit0）
· 需要：更细致地对照 mmc_drv.ko 的 mmc_hw_exec_command 分支逻辑
```

### C. 实现 USB fastboot（工作量大）
```
· 需要：DWC3 控制器（0xF0200000）+ USB PHY 初始化 + gadget + 协议
· 有内核 DWC3 驱动源码可参考（本机有 3.0.27 内核树）
· 一旦成功 = 任意读写 eMMC，但开发量以天计
```

### D. 用 loader 的"读"能力做只读诊断
```
· 让 loader 读 eMMC 后把数据用 LED 或串口输出？
· 没有回传通道（只有 BOOT_SERIAL_IN 是输入）⇒ 需要 USB 或另一路 UART
· 相机侧 DEBUG_UART0_TXD 可能可测（需拆机）
```

## 四、建议的下一步（按顺序）

```
1) 先完成 161 KB loader 传输 + CRC 验证（stage4 loader 模式）
2) 反汇编 loader 的 eMMC 读函数，确定参数
3) 写一个"loader + 我们的 stub"组合：
     段1: blink 程序（0xFE020000）
     段2: loader（0xFE040000）
     段3: stub（0xFE030000）——调用 loader 的 eMMC 初始化 + 读块
   然后让 stub 把读到的内容用 LED 编码报告
4) 若读成功 → 同样方法试写（loader 可能有写函数）
```

## 五、安全边界

```
· 所有写入只发生在 SRAM（0xFE000000~），断电即消失
· 从未写过 eMMC，相机状态未被改变
· 每次测试前需彻底断电（payload 关了看门狗）
```
